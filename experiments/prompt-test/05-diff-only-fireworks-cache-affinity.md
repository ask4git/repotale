# 파이어웍스 모델 호출에 "단골 표시"를 붙일 수 있게 됐습니다

## What

파이어웍스(Fireworks) AI 모델을 호출할 때, "이 요청들은 같은 대화의 연속이다"라는 표시를 붙일 수
있는 옵션이 추가됐습니다. 이 표시를 붙이면 같은 대화의 다음 메시지들이 가능한 한 같은 서버로
몰려가서, 앞서 처리했던 내용을 다시 계산하지 않고 재사용할 수 있게 됩니다.

## Where

`packages/fireworks/src/fireworks-provider.ts`와 `fireworks-chat-options.ts`에 `promptCacheKey`라는
새 옵션이 추가됐습니다. 문서(`content/providers/01-ai-sdk-providers/26-fireworks.mdx`)에 사용
예시 두 가지(단발성 호출, 반복 호출되는 Agent)가 함께 추가됐고, 예제 코드 파일들도 새 옵션을
쓰도록 같이 손봤습니다. 겸사겸사 `kimi-k2p5` 모델 이름이 `kimi-k2p6`으로 바뀌는 작업(구버전
모델은 자동완성 목록에서 제거)도 같은 커밋에 함께 들어갔습니다.

## How

파이어웍스 서버는 캐싱을 자동으로 하지만, 캐시는 요청을 처음 처리했던 "그 서버(replica)"에만
남습니다. 다음 요청이 다른 서버로 가면 캐시를 못 쓰고 처음부터 다시 계산해야 하죠.
`promptCacheKey`는 대화(세션)마다 고정된 값을 하나 정해서 요청에 실어 보내면, 파이어웍스가 같은
키를 가진 요청들을 최대한 같은 서버로 몰아주는 방식입니다.

AI SDK는 하나의 대화 안에서 여러 단계(도구 호출 등)를 거치는 동안 같은 설정을 재사용하기
때문에, 키 하나만 정해두면 그 대화의 모든 단계에 자동으로 같이 적용됩니다. 우체국 비유를 다시
쓰면, 편지 봉투에 "이 사람 담당 집배원에게"라는 스티커를 붙여서, 매번 다른 집배원이 처음부터
주소를 찾아 헤매지 않고 이전에 배달해본 집배원이 계속 담당하게 하는 것과 비슷합니다.

## Why

이번에도 diff에 포함된 문서 설명 덕분에 기술적 동기는 비교적 분명했습니다: "캐시가 서버 하나에만
붙어 있다"는 파이어웍스 캐싱 구조의 특성 때문에, 여러 단계로 이어지는 대화(멀티스텝 도구 호출
등)에서 캐시 적중률이 떨어지는 문제를 보완하려는 목적으로 읽혔습니다.

다만 이번 건은 앞의 MCP 사례보다 살짝 더 조심스러웠습니다. diff 안에는 "왜 하필 지금" 이 옵션을
넣었는지 설명하는 배경 서술(예: 특정 이슈, 사용자 리포트)이 전혀 없었고, 심지어 얼핏 무관해
보이는 모델 이름 변경(`kimi-k2p5` → `kimi-k2p6`)이 같은 커밋에 같이 묶여 들어가 있어서 "이 두
변경이 정말 하나의 동기에서 나온 건지, 아니면 그냥 같이 처리된 별개 작업인지"조차 diff만으로는
확신할 수 없었습니다. PR 본문이 있었다면 이 부분(하나의 PR로 묶은 이유)을 바로 확인했을
텐데, 이번엔 "묶여 있다"는 사실만 적고 이유는 추측하지 않았습니다.
