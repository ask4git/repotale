# 열린 질문: 역질문 쪽지시험 vs "루프에 사람을 넣지 않는다"

> `comprehension-debt-concept.md` 4번(역질문 쪽지시험)과 7번("루프에 사람을 넣지 않는다"
> 원칙)의 충돌, 9번 "열린 질문" 마지막 항목을 다룬다. 결정은 product owner 몫이므로, 여기서는
> 실행 가능한 옵션만 정리한다. 최종 선택은 하지 않는다.

## 충돌의 본질

- 4번 쪽지시험은 구조적으로 **사람의 응답을 기다려야 성립**하는 기능이다 (능동적 회상을
  끌어내는 게 목적이므로, 응답 자체가 산출물이다).
- 7번 원칙은 "이걸 하려면 사람이 뭔가 눌러야/답해야 하는가"를 새 기능의 기본 판정 기준으로
  삼고, 답이 예스면 기본 경로가 아니라 완전 선택적 부가 기능으로만 넣는다고 못박았다.
- 즉 쪽지시험은 정의상 이 판정 기준에 걸린다. 문제는 "그래서 폐기냐, 격하냐, 아니면 원칙 쪽을
  예외 처리하냐"이고, 세 방향 모두 실행 가능하다.

## 옵션

### 옵션 A — 완전 선택적 기능으로 남기고, 계기판 신호로만 흡수

쪽지시험은 로드맵에 유지하되 다음 조건을 강제한다: 응답은 100% 스킵 가능, 응답 여부/정오답이
포스트 발행이나 다음 분석 사이클에 어떤 영향도 주지 않음, 응답 결과는 오직 계기판(2번 원칙)의
보조 입력값으로만 사용.

- 장점: 기능 아이디어 자체는 살리고, 응답을 정말 원하는 PO에게는 "이해도" 신호를 준다.
- 트레이드오프: "완전 선택적"을 지키려면 UI/UX에서 시험을 강조하지 않아야 하는데, 그러면 실제
  응답률이 낮아져서 애초에 계기판에 유의미한 신호를 못 줄 위험이 크다.

### 옵션 B — 로드맵에서 완전히 드롭

쪽지시험 아이디어 자체를 MVP 이후 로드맵에서도 제외한다. "이해했는지 확인"이라는 목적은
계기판 지표(자동 수집 가능한 대리 지표, `open-question-dashboard-metric.md` 참고)만으로
대체한다.

- 장점: 원칙(7번)과의 충돌이 아예 사라진다. 구현 복잡도·UX 복잡도 둘 다 최소.
- 트레이드오프: "읽었다"와 "이해했다"를 구분할 방법이 없어진다. 계기판이 결국 "설명 없이 쌓인
  변경량"처럼 간접 지표에만 의존하게 되고, 코멘션 debt 재정의 3번이 말한 "이해했다는 사실을
  확인하는 장치"가 통째로 빠진다.

### 옵션 C — 원칙에 예외 카테고리를 명시적으로 신설

7번 원칙을 "필수 경로에는 사람을 넣지 않는다"로 좁혀 재정의하고, 쪽지시험처럼 **핵심
파이프라인(분석→클러스터링→발행)과 완전히 분리된 보조 루프**는 원칙의 적용 대상이 아니라고
문서에 명문화한다. 대신 보조 루프에는 별도 하위 규칙을 둔다: 응답 없어도 다음 포스트 발행에
지장 없음, 알림/리마인드는 최대 1회, 미응답이 패널티로 이어지지 않음.

- 장점: 원칙을 지키면서도 쪽지시험처럼 "성격상 사람이 필요한" 보조 기능을 넣을 길을 열어둔다.
  향후 비슷한 충돌(예: 피드백 요청, 수동 태깅)이 생겼을 때도 같은 하위 규칙을 재사용할 수 있다.
- 트레이드오프: 원칙에 예외 카테고리가 생기면 "이것도 예외 아닌가"라는 판단을 매번 새로
  해야 하는 부담이 생긴다. 원칙의 명료함(7번이 의도했던 "판정 기준 하나로 끝")이 옅어진다.

## 결정 필요

위 세 옵션(또는 조합) 중 택 1. 특히 옵션 A와 C는 같이 쓸 수도 있음 — A는 "쪽지시험을 어떻게
만들지"에 대한 답이고, C는 "원칙 문서를 어떻게 고칠지"에 대한 답이라 서로 배타적이지 않다.
