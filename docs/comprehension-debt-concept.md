# 인지부채(comprehension debt) 재정의 & 기능 아이디어

> 작성일: 2026-07-27 · 상태: 아이디어 메모 (repo-story-idea.md 보완)
>
> repo-story-idea.md의 문제 정의(2번)를 더 날카롭게 다듬고, 그 재정의에서
> 파생된 기능 아이디어 3개를 기록한다.

## 1. 포지셔닝: 인지부채는 버그가 아니라 비용이다

바이브코딩이 잘못돼서 인지부채가 생기는 게 아니다. 개발 속도가 사람의
이해 속도를 앞지르는 순간 필연적으로 발생하는 **비용**이다. "당신이
뭔가 잘못했다"는 프레이밍이 아니라 "속도를 낸 대가로 당연히 쌓이는 것"
이라는 프레이밍이어야 한다.

이 관점은 랜딩 카피, 온보딩 메시지, 제품 톤 전반에 일관되게 반영돼야
한다. 죄책감을 자극하는 문구("당신은 코드를 이해 못 하고 있습니다")
대신, 비용 관리 문구("속도를 낸 만큼 쌓인 비용, 관리 가능한 수준으로
유지하세요")로 간다.

## 2. 관리 원칙: 완제 상환이 아니라 이자 감당

기술부채를 다루는 방식(리팩터링 스프린트로 "다 갚기")을 인지부채에
그대로 적용하면 안 된다. 코드 전체를 완벽히 이해하는 상태로 되돌리는
것은 불가능하고, 목표로 삼을 필요도 없다.

대신 관리 기준은 **이자가 감당 가능한 수준인지**다:

- "이해 못 하는 코드의 총량"을 0으로 만드는 게 목표가 아니다.
- "지금 이해 못 하는 부분이 의사결정에 리스크가 될 만큼 커지고 있는가"를
  주기적으로 확인하는 게 목표다.
- 제품 관점에서는 완독을 요구하는 아카이브가 아니라, **위험 신호를
  짚어주는 계기판**에 가까워야 한다. (예: 최근 N주간 설명 없이 쌓인
  변경량, 아무도 질문/확인하지 않은 포스트 비율 등 — 구체 지표는 후속
  설계 필요.)

이 원칙은 MVP 범위(repo-story-idea.md 7번)에는 없던 것이라, 추후
"현재 인지부채 수준" 같은 지표성 기능을 검토할 때 이 원칙을 기준으로
삼는다.

## 3. 핵심 전제: 이해는 자동으로 쌓이지 않는다

블로그 포스트를 자동 발행하는 것만으로는 부족하다. **코드는 쌓이지만
이해는 저절로 쌓이지 않는다** — 이게 이 서비스가 풀어야 할 진짜 문제의
정의다. 포스트를 만들어 놓기만 하고 아무도 안 읽으면, 결국 "읽을 수는
있지만 아무도 안 읽는 아카이브"가 되어 지금의 커밋 로그와 본질적으로
같은 실패를 반복한다.

그래서 **읽었다는 사실이 아니라 이해했다는 사실을 확인하는 장치**가
필요하다 → 4번 아이디어로 이어짐.

## 4. 기능 아이디어: 역질문 쪽지시험

수동적으로 포스트를 읽게 하는 대신, agent가 Product Owner에게 짧은
쪽지시험(pop quiz)을 낸다. "이번 주 추가된 결제 재시도 로직, 실패
3번째엔 어떻게 동작하나요?" 같은 질문에 답하게 해서 실제로 이해했는지
확인한다.

- 목적: 수동적 읽기 → 능동적 회상(active recall)으로 전환. 인지부채를
  "갚는다"는 것은 결국 본인 머릿속에 모델이 남는 것이지, 포스트를
  발행한 것만으로 갚아지지 않는다.
- 질문 소스: 방금 발행된 포스트의 What/Why에서 자동 생성.
- 오답/모름 응답: 벌점이 아니라 신호. "이 부분은 아직 이해도가 낮다"는
  걸 계기판(2번 원칙)에 반영하는 입력값으로 쓴다.
- MVP 범위 밖. repo-story-idea.md 7번 "제외" 항목의 Q&A와 결이 비슷하니
  같이 후순위로 묶어서 설계한다.
- **주의**: 이 아이디어는 7번 "루프에 사람을 넣지 않는다" 원칙과
  정면으로 부딪힌다. 쪽지시험은 구조적으로 사람의 응답을 기다려야
  성립하는 기능이라, 원칙대로면 폐기하거나 완전 선택적(스킵 가능,
  응답 없어도 다음 포스트 발행에 지장 없음)으로 격하해야 한다. 후속
  설계에서 반드시 재검토.

## 5. 기능 아이디어: 문서 스타일 선택 (서술형 / 보고서형)

같은 내용이라도 독자가 받아보는 형식을 고를 수 있게 한다.

- **서술형**: 지금 기획한 "개발 블로그 글" 톤. 이야기로 읽는 방식.
- **보고서형**: 항목/표 중심으로 요약. What/Where/How/Why를 섹션
  헤더로 딱딱 나눠 훑어보는 방식. 바쁜 PM/PO가 스캔하기 편함.

기존 4번 "독자 레벨 토글"(비개발자/개발자 = 깊이 축)과는 다른 축이다.
이건 **문체(narrative vs report)** 축이고, 깊이 축과 직교(orthogonal)
한다. 두 토글이 조합되면 (서술형×비개발자), (보고서형×개발자) 등 4가지
조합이 나올 수 있다는 점을 설계 시 염두에 둔다.

## 6. 기능 아이디어: 리터럴 코드 디프 (literate code diff)

Knuth의 literate programming 아이디어를 diff에 적용. 포스트에서
"근거 커밋 링크"로 빠지게 하는 대신, **diff 자체를 hunk 단위로
주석처럼 설명이 붙은 형태로 렌더링**한다. 코드 옆에 "왜 이 줄을 이렇게
바꿨는지"가 바로 붙어 있는 뷰.

- 기존 계획(repo-story-idea.md 6번 "Why의 복원", 8번 "근거 커밋/PR
  링크를 포스트에 병기")의 구체적인 구현 형태로 볼 수 있다. 링크만
  거는 것보다 훨씬 강한 검증 가능성(hallucination 리스크 완화)을
  제공한다.
- 포스트 안에서 바로 볼 수도, 별도 뷰(예: `/repo/[owner]/[repo]/diff/[sha]`
  같은 라우트)로 뺄 수도 있음 — 배치는 후속 결정.

## 7. 원칙: 루프에 사람을 넣지 않는다

전체 방향은 사람의 개입(승인 대기, 응답 필수, 수동 트리거) 없이 굴러가는
쪽을 추구한다. 분석 → 클러스터링 → 발행까지 사람이 끼지 않고 자동으로
돈다는 게 이미 4번 "제품 컨셉"의 전제(push마다 자동 발행)이기도 하다.

이 원칙을 서비스 전반의 기본값으로 삼는다:

- 새 기능을 설계할 때 "이걸 하려면 사람이 뭔가 눌러야/답해야 하는가"를
  먼저 확인한다. 답이 예스면, 그 기능은 기본 경로가 아니라 완전
  선택적인 부가 기능으로만 넣는다.
- 6번 쪽지시험 아이디어가 이 원칙과 정면 충돌한다 (위 4번 항목 "주의"
  참고). 인지부채를 사람이 직접 갚게 만드는 장치와, 사람 개입을 줄이는
  방향이 같은 서비스 안에서 공존하려면 역할 분리가 필요하다 — 예를
  들어 "쪽지시험 없이도 계기판(2번 원칙)은 자동으로 신호를 낸다"는
  식으로, 사람 응답은 있으면 더 정확해지는 보너스 신호 정도로만 쓰고
  핵심 파이프라인의 필수 조건으로 만들지 않는다.

## 8. 기존 기획서에 미치는 영향

- **2번 문제 정의**: "인지부채는 버그가 아니라 비용" 프레이밍을 문제
  정의 서두에 반영할지 검토.
- **4번 제품 컨셉**: 문서 스타일 토글(5번)을 "독자 레벨 토글"과 나란히
  기록.
- **6번 차별화**: 리터럴 코드 디프(6번)를 "Why의 복원" 항목의 구체
  구현으로 명시.
- **7번 MVP 범위**: 역질문 쪽지시험(4번)은 제외 항목에 그대로 후순위
  유지. 이자 관리 계기판(2번)은 새 항목이라 별도로 후순위 등록 필요.

## 9. 열린 질문

- 계기판(2번) 지표를 뭘로 잡을지 — 설명 없이 쌓인 변경량? 미확인 포스트
  비율? 쪽지시험 오답률? 하나로 정하지 말고 프롬프트 실험 단계에서
  후보 비교.
- 쪽지시험(4번) 응답을 어디까지 강제할지 — 완전 선택, 아니면 포스트
  읽음 처리 조건으로 걸지.
- 리터럴 코드 디프(6번)를 MVP 포스트 포맷에 처음부터 넣을지, 포스트
  본문은 프롬프트 실험(repo-story-idea.md 9번 액션)에서 검증한 뒤
  붙일지.
- 쪽지시험(4번)과 "루프에 사람을 넣지 않는다"(7번) 원칙 충돌을 완전히
  없앨지, 아니면 선택적 부가 기능으로 남겨서 공존시킬지 최종 결정
  필요.
