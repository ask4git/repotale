# 인지부채 해소의 제품 가치와 측정 지표

> 작성일: 2026-08-02 · 상태: 제안
>
> `comprehension-debt-concept.md`의 "이자 감당" 원칙을, 고객에게
> 설명하고 검증할 수 있는 측정 지표로 구체화한다.

## 결론

repotale이 증명해야 할 것은 "AI가 포스트를 몇 개 생성했다"가 아니라,
**제품 변경을 사람이 더 빨리, 더 정확하게 설명할 수 있게 됐다**는 것이다.

인지부채는 코드의 총량이 아니라, 변경이 설명·검증 가능한 상태로 남지 않아
발생하는 비용으로 다룬다. 따라서 지표도 아래 두 층으로 나눈다.

1. **선행 지표**: 변경이 제때, 근거와 함께 설명됐는가
2. **결과 지표**: 그 결과 사람이 변경을 이해하는 데 드는 비용이 줄었는가

선행 지표만 좋으면 "잘 정리된 아카이브"에 머물 수 있다. 결과 지표까지
개선되어야 인지부채를 실제로 낮췄다고 말할 수 있다.

## 고객에게 제시할 수 있는 핵심 수치

| 가치 | 측정값 | 고객에게 말하는 방식 |
| --- | --- | --- |
| 변경 누락 방지 | 설명 커버리지 | "이번 달 변경의 96%가 읽을 수 있는 설명과 함께 남았습니다." |
| 최신성 | merge부터 포스트 발행까지의 시간(p50/p90) | "변경 후 12분 안에 설명이 생깁니다." |
| 근거성 | 원본 PR·diff로 추적 가능한 포스트 비율 | "모든 설명을 원본 변경 근거로 검증할 수 있습니다." |
| 탐색 비용 감소 | 변경 파악 과제를 완료하는 시간 | "10분 걸리던 변경 파악을 2분으로 줄였습니다." |
| 독립적인 이해 | PO/창업자의 핵심 질문 정답률 | "개발자에게 묻지 않고도 변경 이유를 80% 정확도로 설명합니다." |
| 협업 비용 감소 | 개발자에게 들어오는 변경 관련 질문 수·응답 시간 | "상태 공유를 위한 반복 질문을 주당 6건 줄였습니다." |

표의 숫자는 예시이며, 현재 제품의 실측값이 아니다. 파일럿에서 전후 비교로
확보한 데이터만 대외 메시지에 사용한다.

## 첫 번째 핵심 지표

### 1. 설명 커버리지 (Explanation Coverage)

```text
설명 커버리지 =
  근거 링크를 포함한 발행 포스트로 설명된 merge PR 수
  / 전체 merge PR 수
```

"코드는 존재하지만 설명이 없는 변경"을 직접 보여주는 가장 기본적인 지표다.
분모와 분자를 PR로 고정하면 구현이 단순하고, 자동 계산할 수 있다.

- 권장 표시: 최근 7일·30일 커버리지, 설명되지 않은 PR 목록
- 초기 성공 기준: 최근 30일 90% 이상
- 주의: 포스트가 존재한다는 사실은 이해를 보장하지 않는다. 아래 결과 지표와
  반드시 함께 본다.

### 2. 변경 이해 시간 (Time to Understand)

사용자 가치에 가장 가까운 결과 지표다. 같은 변경에 대해 참가자에게
"무엇이 바뀌었고, 왜 바뀌었나?"를 묻고, 답을 찾고 설명하는 데 걸린 시간을
측정한다.

- 비교군: GitHub/커밋 로그와 개발자 질의에 의존하는 현재 방식
- 실험군: repotale 포스트와 원본 근거 링크를 사용하는 방식
- 함께 기록할 값: 완료 시간, 답변 정확성, 답변을 위해 개발자에게 질문한 횟수
- 초기 성공 기준: 완료 시간 50% 이상 감소, 정확성 저하 없음

시간만 짧고 답이 틀리면 제품 가치가 아니다. 정확성은 미리 준비한
What/Why 질문과 채점 기준으로 함께 본다.

## 인지부채 계기판: 단일 점수보다 행동 가능한 신호

초기에는 여러 성격의 값을 하나의 "인지부채 점수"로 합산하지 않는다. 변경량,
지연, 독자 이해를 임의 가중치로 섞으면 점수는 보기 좋지만 원인을 찾기 어렵고
게임하기도 쉬워진다. 아래 지표를 나란히 보여주는 편이 더 정직하고 행동 가능하다.

| 계기판 항목 | 정의 | 측정 방식 | 의미 |
| --- | --- | --- | --- |
| 미설명 변경 수 | 포스트로 커버되지 않은 merge PR 수 | 자동 | 당장 설명 자산이 비어 있는 범위 |
| 미설명 변경의 경과 시간 | merge 후 아직 설명되지 않은 시간의 p90/최대값 | 자동 | 방치되어 쌓이는 인지부채의 이자 |
| 설명 커버리지 | 설명된 merge PR / 전체 merge PR | 자동 | 변경이 자산으로 전환되는 비율 |
| 발행 지연 | merge부터 발행까지의 시간 p50/p90 | 자동 | 설명이 변경 속도를 따라가는 정도 |
| 확인 비율 | 열람 또는 선택적 이해 확인을 완료한 포스트 / 발행 포스트 | 사용자 이벤트 | 설명이 실제로 닿았는지에 대한 보조 신호 |

`미설명 변경 수`와 `발행 지연`은 사람 개입 없이 측정할 수 있어 MVP 이후
가장 먼저 붙일 후보이다. `확인 비율`은 열람이 곧 이해를 뜻하지 않으므로,
선택적 쪽지시험이나 후속 이해도 조사와 결합할 때만 강한 지표가 된다.

## 파일럿 검증 설계

초기 5개 내외의 repo에서 아래 전후 비교를 한다.

1. 최근 변경 3~5개를 선정하고, PO/창업자에게 What/Why 질문을 준다.
2. 현재 도구(GitHub, Slack, 개발자 질의)만으로 답하는 시간·정확성·질문 횟수를 기록한다.
3. 동일한 난이도의 별도 변경에 repotale 포스트를 제공하고 같은 값을 기록한다.
4. repo 단위로 설명 커버리지와 발행 지연도 함께 기록한다.

첫 파일럿의 성공 기준은 다음과 같다.

- 설명 커버리지: 90% 이상
- 발행 지연: p90 24시간 이내
- 변경 이해 시간: 기존 방식보다 50% 이상 감소
- 정확성: 기존 방식 대비 하락하지 않음

표본이 작을 때는 평균만 내세우지 않고 repo별 원자료와 과제 난이도도 함께
검토한다. 이 결과가 생긴 뒤에야 "몇 분 절감", "몇 % 커버" 같은 숫자를
랜딩과 세일즈에서 주장한다.

## 비용 절감으로 환산하기

고객별 ROI는 다음처럼 투명하게 계산한다.

```text
월 절감 시간 =
  변경 파악 시간 감소
  + 개발자의 변경 관련 질의 응답 시간 감소
  + 온보딩/인수인계 시간 감소

월 절감 비용 = 월 절감 시간 × 해당 인력의 시간당 완전비용
```

예를 들어 월 12시간을 줄이고 시간당 완전비용이 7만원이면 월 절감 비용은
84만원이다. 이 계산은 고객의 실제 시간·인건비를 입력해 제시하며, 일반화된
성과 수치처럼 사용하지 않는다.

## 제품 계측에 필요한 최소 이벤트

대외 성과를 말하려면 먼저 아래 데이터를 저장해야 한다.

- `pr_merged`: PR 번호, merge 시각
- `post_published`: 대응 PR 번호, 발행 시각, 원본 PR/diff 링크 유무
- `post_opened`: 사용자, 포스트, 열람 시각
- `understanding_check_completed` (선택): 질문, 응답, 채점 결과
- `change_question_logged` (파일럿 한정): 변경 관련 질의가 개발자에게 전달된 시각과 해결 시각

포스트와 PR의 대응 관계는 커버리지·지연·근거성을 계산하는 최소 전제다.
사용자 응답 이벤트는 기본 발행 파이프라인을 막지 않는 선택 기능으로 둔다.

## 현재 구현과의 구분

현재 코드에는 최근 merge PR을 가져와 제목·요약·태그와 PR 링크를 생성하는
파이프라인 기반이 있다. 하지만 repo 화면은 아직 하드코딩된 데모 포스트를
사용하며, GitHub webhook에서 실제 분석을 실행하는 부분도 TODO다. 생성 결과는
현재 What 중심의 요약이며, 기획의 What/Where/How/Why 전체를 별도 구조로
저장하지 않는다.

그러므로 지금은 위 수치를 제품 성과로 주장할 단계가 아니라, 이를 검증할
계측과 파일럿을 설계하는 단계다. 자동 발행과 PR-포스트 저장 연결이 갖춰지면
설명 커버리지·발행 지연·근거성부터 즉시 측정할 수 있다.
