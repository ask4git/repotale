# 라이선스 옵션 비교 — Fair-Source 계열 3종

> self-host 버전과 cloud 유료 버전을 동시에 운영하는 구조(n8n류 모델)를 전제로, 실제로 쓰이고
> 있는 "fair-source" 성격의 소스 공개 라이선스 3개를 비교한다. 리서치 목적 문서이며, 라이선스
> 채택 여부는 이전 대화에서 이미 product owner 결정 사항으로 보류됐다. 여기서는 최종 추천을
> 하지 않는다.

세 라이선스 모두 소스코드는 공개하되(오픈소스 정의상의 "오픈소스"는 아님), **경쟁 호스팅
서비스로 되파는 것**을 막는다는 공통 목적을 가진다. 차이는 "얼마나 세밀하게 막는가"와 "언제/어떻게
완전 오픈소스로 전환되는가"에 있다.

## 1. Business Source License 1.1 (BSL 1.1)

- **실제로 막는 것**: 라이선스 본문 자체는 막는 게 거의 없다 — 대신 프로젝트마다 별도로 붙이는
  "Additional Use Grant" 조항에서 구체적으로 금지 범위를 정의한다. 가장 흔한 패턴은 "이 소프트웨어를
  이용해 제3자에게 상용 관리형 서비스(managed/hosted offering)를 제공하는 것"을 금지하는 것.
  즉 라이선스 자체가 아니라 프로젝트별 커스터마이즈가 실질적인 제약 범위를 결정한다 — 프로젝트마다
  조항을 따로 읽어야 정확한 제약을 알 수 있다는 뜻이기도 하다.
- **change date / 전환 조건**: 라이선스에 프로젝트가 직접 명시하는 "Change Date"가 있고, 그 날짜가
  지나면 자동으로 지정된 오픈소스 라이선스(대개 Apache 2.0 또는 GPLv2)로 전환된다. Change Date는
  버전 릴리스 시점 기준으로 프로젝트가 자유롭게 정하며, 관행적으로 릴리스로부터 최대 4년 정도가
  많이 쓰인다. 버전마다 개별적으로 Change Date가 붙으므로, 오래된 버전부터 순차적으로 오픈소스화
  되는 구조가 된다.
- **실제 사용 사례**: MariaDB(이 라이선스를 처음 만든 회사, MariaDB Server 일부 컴포넌트에 적용).
  HashiCorp도 2023년 Terraform/Vault 등 핵심 제품을 MPL에서 BSL로 전환했다(이후 이 결정이
  OpenTofu 포크를 촉발한 사례로 업계에 널리 알려짐 — "커뮤니티 반발 리스크"를 참고할 때 같이
  살펴볼 만한 선례).

## 2. Elastic License 2.0 (ELv2)

- **실제로 막는 것**: 세 가지로 명확히 고정돼 있다 — ① 소프트웨어를 제3자에게 관리형/호스팅
  서비스로 제공하는 것 금지, ② 라이선스 키로 잠긴 기능을 우회하는 것 금지, ③ 라이선스 고지 문구
  제거 금지. BSL과 달리 프로젝트마다 조항을 커스터마이즈하지 않는 고정 텍스트라, 어느 프로젝트에
  적용됐는지와 무관하게 제약 범위가 동일하다 — 예측 가능성은 BSL보다 높다.
- **change date / 전환 조건**: **없음.** ELv2 자체에는 일정 기간 후 오픈소스로 자동 전환되는
  조항이 없다. 오픈소스로 되돌리려면 라이선스를 다시 바꾸는 별도의 결정이 필요하다 — 실제로
  Elastic은 2021년 Apache 2.0에서 ELv2/SSPL 이중 라이선스로 전환했다가, 2024년에 다시 AGPL v3를
  옵션으로 추가하는 별도 결정을 내렸다(자동 전환이 아니라 회사의 능동적 재라이선싱).
- **실제 사용 사례**: Elastic(Elasticsearch, Kibana) — 라이선스를 만든 당사자이자 대표 사례.

## 3. Functional Source License (FSL)

- **실제로 막는 것**: "경쟁 사용(Competing Use)" 하나로 단순화돼 있다 — 소프트웨어의 기능을 제3자에게
  제공하는 경쟁 제품/서비스를 만드는 것, 또는 그 기능을 대체하는 용도로 쓰는 것. BSL의
  Additional Use Grant처럼 프로젝트별 세부 조항을 따로 만들 필요가 없어 채택 절차가 가장 가볍다.
- **change date / 전환 조건**: 릴리스 후 **정확히 2년**이 지나면 자동으로 오픈소스 라이선스로
  전환된다 — 3개 중 전환까지 걸리는 기간이 가장 짧고, 기간 자체가 라이선스에 고정돼 있어 BSL처럼
  프로젝트가 임의로 늘릴 수 없다. 전환 대상 라이선스는 Apache 2.0 또는 MIT 중 하나를 프로젝트가
  채택 시점에 선택한다(이후 버전마다 바꾸지 않는 게 일반적).
- **실제 사용 사례**: Sentry — FSL을 처음 설계하고 sentry.io 코드베이스에 실제로 적용한 당사자.

## 요약 비교

| | 제약 방식 | 오픈소스 전환 | 대표 사례 |
|---|---|---|---|
| BSL 1.1 | 프로젝트별 커스텀 조항 (세밀하지만 예측 어려움) | 있음, 기간은 프로젝트가 지정 (관행상 최대 ~4년) | MariaDB, HashiCorp(구 Terraform/Vault) |
| Elastic License 2.0 | 고정 조항 3가지 (예측 쉬움) | 없음 (재라이선싱은 별도 결정 필요) | Elasticsearch, Kibana |
| FSL | 고정 조항 1가지, 가장 단순 | 있음, 정확히 2년 (가장 빠름, 고정) | Sentry |

참고: n8n이 실제로 쓰는 라이선스는 이 3개와 다른, n8n 자체 제정 "Sustainable Use License"(자체
fair-code 라이선스)다. 앞선 대화에서 참조점으로 언급된 건 n8n의 **self-host 무료 + cloud 유료
이원화 전략**이지, 라이선스 문구 자체를 그대로 따온 게 아니라는 점은 구분해둔다.

## 결정 필요

세 라이선스 모두 채택 가능한 후보이며, 선택은 보류 상태다. public 전환 시점에 재논의한다.
