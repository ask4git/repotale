# 사용자 페인포인트 개선 아이데이션

> 작성일: 2026-08-02 · 상태: 제안

## 요약

repotale의 가장 큰 개선 기회는 "글을 자동 생성한다"에서 멈추지 않고,
**사용자가 지금 알아야 할 변경을 신뢰하며 빠르게 이해하고 행동하게 만드는 것**이다.

- **대상 사용자**: 바이브코더, PO/PM, 비개발자 창업자
- **사용자·제품 목표**: 개발자에게 묻지 않고도 "무엇이 왜 바뀌었고, 지금 확인할 것은 무엇인지" 파악하게 한다.
- **성공 신호**: 변경 파악 시간 감소, 반복 질문 감소, 설명 커버리지·발행 지연 개선
- **이번 범위**: 핵심 경험 개선 아이디어와 우선순위. 구현 설계와 개발 일정은 포함하지 않는다.

## 확인된 맥락과 가정

### 확인된 맥락

- 현재 제품은 GitHub 변경을 비개발자도 읽을 수 있는 포스트로 재구성하는 것을 핵심 가치로 둔다.
- 현재 원격 repo 화면은 포스트 목록 중심이며, 분석 결과가 없을 때는 완료를 기다리는 상태만 보여준다.
- 생성 프롬프트는 diff와 PR 설명에 없는 사실을 만들지 않도록 요구하지만, 결과 데이터는 현재 제목·요약·태그·PR 링크 중심이다.
- 기획 문서는 자동 발행한 포스트가 읽히지 않으면 기존 커밋 로그와 같은 실패를 반복할 수 있다고 명시한다.

### 가정

- PO/창업자는 모든 변경을 읽기보다, 자신의 의사결정·검증에 영향을 주는 변경부터 알고 싶어 한다.
- `Why`의 근거가 분명하지 않은 설명은 단기 가독성을 높여도 장기 신뢰를 낮출 수 있다.

이 가정은 파일럿 사용자 관찰과 변경 이해 시간 테스트로 검증해야 한다.

## 개선 기회

| 우선순위 | 사용자 페인포인트 | 개선 아이디어 | 기대 효과 |
| --- | --- | --- | --- |
| P0 | 포스트가 쌓여도 "그래서 지금 뭘 알아야 하지?"가 보이지 않는다. | **이번 주 변경 브리핑**: 새 기능, 영향받는 영역, 확인이 필요한 변경을 최대 3개로 요약한다. | 블로그 아카이브를 실무용 현황판으로 전환한다. |
| P0 | AI가 쓴 `Why` 설명을 신뢰하기 어렵다. | **근거 수준 표시**: `PR에 명시됨` / `diff에서 확인됨` / `근거 부족`을 표시하고 원문으로 연결한다. | 환각 리스크를 투명하게 관리하고 검증 가능성을 높인다. |
| P0 | PO는 기술 상세보다 사용자·사업 영향을 먼저 알고 싶다. | 포스트 첫 화면에 **변경 요약 카드**를 둔다: 사용자 영향, 바뀐 동작, 결정 배경, 주의점. | 읽기 전에 관련성을 판단할 수 있다. |
| P1 | 변경이 많아지면 중요한 내용과 잡음이 섞인다. | **변경 성격 필터**: 사용자 기능, 버그 수정, 운영·보안, 내부 정리로 분류한다. | 비개발자가 봐야 할 변경부터 읽게 한다. |
| P1 | "설명은 있다"와 "이해했다"는 다르다. | **선택형 확인 질문**: 포스트 끝에 10초 내 답할 수 있는 질문 또는 `이해됨` / `질문 있음` 반응을 제공한다. | 강요 없이 이해 부족 신호를 수집한다. |
| P1 | 글마다 맥락을 다시 조립해야 한다. | **기능 타임라인**: 여러 PR을 하나의 기능 서사로 묶고 현재 상태와 변경 이력을 연결한다. | 커밋 단위가 아닌 제품 단위로 이해하게 한다. |
| P2 | 이해가 늦어지는 위험을 알아차리기 어렵다. | **인지부채 신호등**: 미설명 변경 수, 발행 지연, 근거 부족 설명 비율을 분리 표시한다. | 단일 점수 대신 원인별로 행동할 수 있다. |

## 추천: 최소 유효 다음 단계

**`이번 주 변경 브리핑`과 `근거 수준 표시`를 먼저 검증한다.**

이 조합은 두 가지 핵심 실패를 직접 줄인다.

1. 사용자가 자동 생성된 글을 다시 찾아 읽어야 하는 탐색 비용
2. AI가 복원한 설명을 믿어도 되는지 판단하는 검증 비용

쪽지시험, 이해도 계기판, 전체 기능 타임라인은 이 기본 경험이 실제로 읽히고 신뢰받는다는 증거가 생긴 뒤에 우선순위를 재평가한다.

## 사용자 스토리와 수용 기준

### 사용자 스토리

> PO로서 나는 이번 주 제품 변경 중 내 의사결정이나 검증이 필요한 내용을 한 화면에서 확인하고, AI 설명의 근거도 검증하고 싶다.

### 수용 기준

- Given 최근 7일의 분석된 변경이 있을 때, When 저장소 첫 화면을 열면, Then 최대 3개의 핵심 변경과 각각의 사용자 영향·근거 링크가 보인다.
- Given `Why`를 뒷받침하는 PR 설명이나 diff가 없을 때, When 포스트를 볼 때, Then 추정처럼 표현하지 않고 `근거 부족`으로 표시한다.
- Given 사용자가 기술 상세가 필요 없을 때, When 변경 요약 카드만 읽으면, Then 무엇이 바뀌었는지와 확인이 필요한지를 파악할 수 있다.
- Given 사용자가 원문을 확인하고 싶을 때, When 근거 수준 또는 근거 링크를 선택하면, Then 대응하는 PR 또는 diff의 위치로 이동할 수 있다.

## 출시 전 검증

파일럿 repo 5개 내외에서 기존 포스트 목록 경험과 제안 경험을 비교한다.

- 과제: 최근 변경에 대해 "무엇이 바뀌었고 왜 바뀌었는가, 무엇을 확인해야 하는가"를 설명한다.
- 측정: 과제 완료 시간, 답변 정확성, 개발자에게 질문한 횟수, 근거 링크 사용 여부
- 초기 통과 기준: 기존 방식보다 변경 이해 시간 50% 이상 감소, 정확성 하락 없음
